# ATLAS MAX Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the first production-capable ATLAS MAX increment with server-authoritative plans/entitlements, provider-neutral governed routing, usage/evidence controls, and evidence-backed UI states.

**Architecture:** Extend existing ATLAS identity, execution, assistant, service, and UI foundations rather than creating a parallel platform. Keep catalog, entitlement, routing, governor, evidence, and UI contracts isolated; all privileged decisions remain server-authoritative and fail closed.

**Tech Stack:** TypeScript, React 18, Vite, Vitest, existing ATLAS services/runtime, existing design tokens and verification scripts.

**Spec:** `docs/superpowers/specs/2026-10-04-atlas-max-design.md`

## Global Constraints

- Plans: ATLAS Core, ATLAS Pro, ATLAS MAX; prices/quotas/storage/model availability/speed classes/credits/features are configuration, never frontend constants.
- Authorization is tenant-scoped and deny-by-default.
- Provider credentials remain server-side.
- Provider routing is neutral and cannot weaken mandatory privacy/security constraints during fallback.
- Speed classes are `Standard`, `Fast`, `MAX`; requested speed is not a guarantee.
- Evidence is required before UI claims active, paid, running, completed, available, deployed, or verified.
- No unlimited-compute/storage claim and no automatic external-capacity purchase.
- Existing ATLAS security, CI, design, navigation, build, deployment, and production P0 gates remain mandatory.

## Review Focus

1. Forged client-side MAX state must not produce an entitlement; server decision wins.
2. Cross-tenant resource identifiers must be denied even when the actor has MAX in another tenant.
3. Provider outage/fallback must not weaken mandatory privacy/security constraints.
4. Missing or failed metering/evidence must never produce optimistic completion or unaccounted successful metered work.
5. Duplicate billing lifecycle events must be idempotent and must not duplicate entitlement activation.
